# 架构与扩展规范

mudcore 是可被 MUDLIB 按需依赖的通用 LPMUD 框架，不是要求整套采用的游戏。新项目可采用默认组合；老 MUD 可保留自己的 master、登录与玩法，仅接入满足依赖的组件。具体依赖见 [模块契约](module-contracts.md)，配置步骤见 [接入指南](integration.md)。

## 分层与责任

| 层次 | 实现位置 | 责任与边界 |
| --- | --- | --- |
| 驱动适配 | `system/kernel/`、`include/` | master apply、simul efun、UID 与能力检测；权限默认值不是生产安全方案 |
| 基础机制 | `inherit/` | 属性、消息、行动限制、命令、移动、存档；通过接口协作，不内置游戏规则 |
| 可选系统 | 组件与 `system/daemons/` | 战斗、状态、任务、组队、网络、DB、协议、TUI；选用时满足各自依赖 |
| 默认组合 | `living.c`、`user.c`、`system/object/` | 提供可直接扩展的组合与连接生命周期，不代表所有游戏必须采用 |
| 宿主策略 | MUDLIB 自己的目录与配置 | 名称/性别、初始属性、命令集、世界内容、ACL、业务服务和运营配置 |

依赖方向是宿主选择框架机制；框架通过公开别名和约定的钩子调用宿主策略，不反向引用某个游戏的固定路径。HTTP、Socket、TLS、数据库、外部命令、Intermud 都是合理的框架能力；由宿主提供目标、凭据、权限和调用时机，不能以解耦为由删除它们。

## 组合与替换

`CORE_*` 固定指向框架原始实现；`_MODULE`、daemon、对象别名允许宿主在 `<mudcore.h>` 之前定义。组合对象应使用别名，宿主扩展实现应继承 `CORE_*`，避免别名递归。不要为局部策略复制整个认证或命令入口。

默认 `_USER → CORE_USER → _LIVING` 继续组合战斗、状态、组队、任务、战斗记录与 GMCP。新增 `_USER_BASE → CORE_USER_BASE` 仅组合 `_ACTION`、`_COMMAND`、`_DBASE`、`_MESSAGE`、`_MOVE`、`_NAME`、`_SAVE`。它是组件组合，不是独立连接对象。

选择最小组合还需：将 `_USER` 指向 `_USER_BASE`，选择满足依赖的命令阶段与命令文件，按需关闭 parser，并通过 `CHAR_D` 定义初始属性。默认 `USER_OB` 仍管理连接、激活和重连。不能承诺只改一个宏就让所有 RPG 命令自动兼容非 RPG 玩家。

## 扩展约束

- 命令采用受控阶段列表和 protected 钩子。`command_hook()` 等公共入口保持 `nomask`；输入不能充当任意方法名。默认顺序不变。
- 名称/性别是角色策略，认证、UID 导出和连接交接仍由登录流程管理；策略钩子不能制造认证状态。初始属性继续使用 `CHAR_D`，不新增第二套角色工厂。
- 编译选项与别名在对象编译时生效；命令阶段在启用时验证并保存。没有运行中热切换组件或认证策略的保证。
- “可选”必须有明确能力检查与缺席测试。协作者存在但抛错时传播错误，不能用宽泛 `catch` 把真实故障伪装成未启用。
- 默认 master 较宽松的文件和 Socket 策略由宿主按生产要求替换。`_HOST_POLICY` 只报告实现来源，不认证策略安全，也不修改授权结果。

## 生命周期、兼容与验证

组件继承本身不等于启动服务。由组合对象或宿主负责初始化、心跳、保存、断线与销毁；异步组件按各自接口取消请求、定时任务和连接。不要把对象属性、DBSAVE 的集中存档和 SQL 数据库混为一种持久化机制。

新增公共组件必须登记依赖矩阵，写明输入/返回、错误、初始化与清理、驱动包和宿主责任。公开 API、默认组合、存档字段与别名兼容性受 [版本规范](maintenance.md) 约束；主动切换组合的现有玩家需宿主单独评估存档，不自动迁移。

[回归入口](../tests/README.md) 同时验证默认、宿主覆盖、物理省略未选组件的最小组合和自定义策略。必须覆盖可选协作者缺席、正常存在及抛错；隔离宿主通过不等于实际老 MUD/minimud/MyMud 已验收。裁剪驱动的支持只能以实际裁剪构建结果证明。
