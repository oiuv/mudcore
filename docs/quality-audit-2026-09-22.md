## 不得改变的框架边界

mudcore 是通用 LPMUD 框架，支持新 MUD 开发及老 MUD 按需集成。Socket、HTTP/HTTPS、TLS、数据库（包括本地 SQLite）、外部命令及 Intermud 协议均属于合理的框架能力。

框架不应内置具体运营服务地址、凭据或默认主动调用。MUDLIB 决定使用哪些模块、如何配置以及何时调用；具体第三方业务适配放在 MUDLIB。不能通过删除或禁用通用能力来“修复依赖”。详见 [框架能力与业务依赖边界](dependency-boundary.md)。

## 修复前缺陷详情与验收要求

### MC-001：HTTP 响应被截断

**位置：** [inherit/Http.c](../inherit/Http.c)，`receive_data()`，审查时第 41 行。

收到第一个数据块后，代码根据请求头中的 `Connection` 判断是否关闭连接；默认未提供该请求头时也立即关闭，没有确认完整响应是否已经收到。

真实本机 TCP 复现：服务端声明 `Content-Length: 6`，先发送响应头及 `abc`，延迟后发送 `def`；客户端最终只收到 `abc`。

这不是单纯“按数据块回调”的接口设计问题，而是框架提前关闭连接。使用方只在 `response()` 中拼接字符串，无法补回后续丢失的数据。较大响应、分段发送及慢速网络都可能触发。

修复应正确处理响应完成条件和连接生命周期，保留通用 HTTP 能力及现有接口的兼容性，不能要求每个业务调用者自行修补传输层。

- [x] 延迟分两次发送的六字节响应完整得到 `abcdef`。
- [x] 响应头自身分段、正文多段到达时，不提前关闭连接。
- [x] 覆盖 Content-Length、chunked、对端关闭等不同响应结束条件；明确支持范围。
- [x] 异常中断不能被误报为完整成功，连接及请求状态正确清理。

### MC-002：HTTP 并发请求关联与失败清理

**位置：** [inherit/Http.c](../inherit/Http.c)，`connect()`、`on_resolve()`、`request()`，审查时第 56、72、182 行。

`Host_fd[host]` 每个域名只保存一个描述符，新请求覆盖旧请求；解析回调通过域名取描述符，没有使用解析请求标识关联原请求。DNS 失败分支没有关闭待处理连接，超时和状态清理也不完整。

回调级模拟中，两个同域名请求持有 `1001`、`1002`，两次解析完成回调均转向 `1002`；失败回调也未清理待处理连接。这是状态逻辑复现，不是完整的真实 DNS 并发测试。

影响是同一个 daemon 并发请求同一服务时可能请求遗漏、重复连接及资源滞留。应按请求标识管理解析与连接，明确失败、超时、关闭时的清理规则。

- [x] 同域名的两个并发请求分别完成，不覆盖、串用或遗漏描述符。
- [x] 覆盖同域名不同端口、解析失败及解析回调晚于取消的情况。
- [x] DNS 失败、连接失败和超时均提供明确结果，并释放 socket 及请求状态。
- [x] 回调模拟之外补充可控的解析/连接集成测试，不依赖真实运营服务。

### MC-003：默认登录辅助接口的身份导出边界

**位置：** [system/daemons/login_d.c](../system/daemons/login_d.c) 的 `make_body()`（第 135 行）、[system/object/user.c](../system/object/user.c) 的 `setup()`（第 20 行），以及 [master/valid.c](../system/kernel/master/valid.c) 的权限检查。

新增检查确实拒绝非 Root 对象直接 `seteuid(ROOT_UID)`，也拒绝跨 UID 的函数绑定。但公开的 `make_body()` 没有验证调用者或传入 ID，就进行身份切换和 `export_uid()`。

默认框架隔离环境中的复现步骤：

1. 由非 Root LPC 对象构造一个 `id` 为 `Root` 的对象。
2. 调用 `LOGIN_D->make_body()`。
3. 对返回玩家对象调用 `setup()`。
4. 实际得到 UID、EUID 均为 `Root` 的玩家对象。

**已证明的是非特权 LPC 调用者能制造特权对象，不是普通玩家通过网络输入即可提权，也不是当前老 MUD 已被证明存在相同漏洞。** 新增直接权限检查没有闭合这条既有调用链，不能将其描述为完整的权限安全修复。

- [x] 非可信调用者不能通过登录辅助接口创建 Root 或任意其他用户身份对象。
- [x] 验证调用来源、登录状态、保留身份及身份导出条件，而非只拦截字面值 `Root`。
- [x] 正常登录仍能设置正确 UID/EUID、存档路径及进入游戏状态。
- [x] 检查其他公开的身份切换/导出入口，并分别验证默认 master 与宿主覆盖策略。

### MC-004：谓词重载出现空索引窗口

**位置：** [system/daemons/verb_d.c](../system/daemons/verb_d.c)，`eventReloadVerbs()`、`scheduledVerbLoad()`、`rehash()`，审查时第 64 行立即清空索引，第 77 行延迟加载。

本次新增 `Verbs = ([])` 后，再通过一秒后的 `call_out()` 分批加载，导致热重载期间索引不可用。

实测重载前有两个谓词，调用 `rehash()` 后索引立即为空；连续重载两次，存在两组未取消的加载任务。清空索引是新增回归，旧任务缺少取消/失效机制则是原有异步管理不足。

应在临时索引中构建成功后统一替换，并隔离过期批次。不要把登录 daemon 的 `create()` 调用重载误描述为“每次玩家登录都重载”。

- [x] 重载构建期间原有可用谓词继续可用。
- [x] 重复重载不会由旧任务覆盖新结果或反复销毁、加载同一对象。
- [x] 加载失败有明确策略，不导致整个有效索引丢失。
- [x] 正确移除已删除谓词，并继续支持 `.c`、`.lpc` 和同义词。

### MC-005：Intermud 域名对端静默失败

**位置：** [system/daemons/intermud/i2d.c](../system/daemons/intermud/i2d.c)，`start()`（第 68 行）、`send_event()`（第 264 行）。驱动依据：宿主 `fluffos/src/packages/sockets/socket_efuns.cc` 第 208 行附近。

`start(host, port, bindPort)` 接受域名，但只解析本机名称，没有解析对端。发送时直接把对端字符串交给 socket，并忽略发送返回值；当前驱动在该路径要求数字地址。

真实本机 UDP 验证：

| 对端 | `start()` 返回 | 收到的初始报文 |
| --- | --- | --- |
| `127.0.0.1` | 1 | 2 |
| `localhost` | 1 | 0 |

这说明本地 socket 启动成功不等于对端通信成功。应支持对端解析，或者明确限制为数字地址并拒绝域名，不能无提示接受后失效。

- [x] 数字地址和声明支持的域名均可向本机测试对端发送初始报文。
- [x] 解析、绑定、发送失败有明确结果，不静默报告可用。
- [x] 停止、重复启动、切换对端行为符合接口说明。
- [x] 默认加载仍不启动网络，不重新引入固定中心地址。

### MC-006：`read_lines()` 改变有效行内容

**位置：** [system/kernel/simul_efun/file.c](../system/kernel/simul_efun/file.c)，`read_lines()`，审查时第 23 行。

新增的 `map(... trim ...)` 不只过滤空行和注释，还改变返回行的内容。实测输入 `"  preserve spaces  "`，返回 `"preserve spaces"`。

该通用函数不只用于配置。老 MUD 的 `inherit/char/char.c` 第 199 行使用 `read_lines(NOTICE)` 读取公告，因此存在缩进、对齐等兼容风险；本次没有证明实际公告已显示异常。

应使用裁剪后的内容判断空行/注释，但保留有效行原文；配置字段需要裁剪时在配置解析处处理。

- [x] 普通有效行保留前后空格。
- [x] 空行、缩进注释和 CRLF 按约定处理。
- [x] 预加载路径与 `.env` 解析仍正常。
- [x] 核对公告等非配置调用者，并记录必要的迁移说明。

### MC-007：HEAD 查询参数丢失

**位置：** [inherit/Http.c](../inherit/Http.c)，`head()`（第 220 行）及 `request()` 的查询参数分支。

`head()` 接受 `query`，但构造请求时只有 `GET` 分支追加参数。传入 `([ "q": "x" ])` 后，实测生成 `HEAD /head HTTP/1.1`，而非 `HEAD /head?q=x HTTP/1.1`。

- [x] GET 与 HEAD 统一处理查询参数。
- [x] 覆盖已有查询字符串、空 mapping、中文及保留字符编码。
- [x] HEAD 的无响应正文语义与 MC-001 的响应完成判断一致。

### MC-008：TLS 默认行为说明不准确

**位置：** [Socket.md](Socket.md) 第 180 行附近、[inherit/Socket.c](../inherit/Socket.c) 的 `create_socket()`、[inherit/Http.c](../inherit/Http.c) 的 `open_http_socket()`。驱动依据：宿主 `fluffos/src/packages/sockets/socket_efuns.cc` 第 903 行附近。

文档把 `CORE_SOCKET`、`CORE_HTTP` 一并描述为“TLS 默认验证对端证书”。实际只有新增 HTTP 初始化明确设置 `SO_TLS_VERIFY_PEER = 1`；通用 Socket 的 TLS 创建分支没有设置，当前驱动未启用该选项时使用 `SSL_VERIFY_NONE`。

- [x] 文档区分 HTTP 封装、通用 Socket 和原始 efun 的默认行为。
- [x] 若调整实现的安全默认值，记录兼容影响和宿主配置方式。
- [x] 用本机可控 TLS 服务覆盖可信、不可信及主机名不匹配证书；记录驱动实际支持范围。
- [x] 不将“成功设置选项”描述为“已验证真实证书握手安全”。

## 配置限制与验证缺口：SQLite

这项不按新增缺陷计数。默认 [master/valid.c](../system/kernel/master/valid.c) 的 `valid_database()` 在连接时返回 `DB_PASSWORD`；未配置时返回 `0`。当前驱动将 `0` 解释为拒绝连接，而不是“允许无密码连接”。依据为宿主 `fluffos/src/packages/db/db.cc` 第 177 行附近。

隔离环境中，未配置密码和数据库授权策略的 SQLite 连接报 `Database security violation attempted`。这并不意味着 SQLite 需要外部服务，也不意味着应将数据库权限全部放开。

- [x] 明确宿主如何按调用者、本地路径和数据库类型授权 SQLite。
- [x] 验证获准本地数据库的连接、建表、读写、关闭，以及未授权访问被拒绝。
- [x] 不再以“对象可以加载”或“默认无凭据”代替数据库功能验证。
