## 任务系统QUEST

在游戏中总是有各种各样的任务，这里的任务系统是指有任务发布人（领取任务）和任务奖励人（完成任务）和具体要求的任务，如果是无需领取只是达成条件就可以获得奖励的任务（如悬赏）可参考 `EVER_QUEST_D` 自由任务机制，并由宿主实现具体任务规则。

### 任务系统相关文件

- `QUEST_D`：任务守护进程。
- `CORE_USER_QUEST` / `_USER_QUEST`：玩家任务状态与管理接口，默认 `CORE_USER` 已组合该组件；任务状态随玩家对象存档，组件自身不负责调用存档流程。
- 任务文件：具体任务规则，参考 [example.c](../world/quest/example.c)。

另外需要在游戏中增加相关指令来接受任务和完成任务，具体调用以下接口：

```c
// 接受任务
QUEST_D->offer_quests(npc, me);
// 完成任务
QUEST_D->reward_quests(npc, me);
```

同时还需实现一个任务管理指令，方便玩家查看自己任务信息。

### 索引与交付顺序

`QUEST_D` 创建时恢复已保存的发布人/奖励人索引，不自动扫描全部任务文件。新增、删除或修改任务的发布人后，调用 `scan_quests()` 重建默认 `QUEST_DIR`，也可传入目录；每次扫描替换整套索引。扫描失败保留旧索引并传播异常，空目录清空旧索引。任务身份、条件、消息及奖励接口以 [任务示例](../world/quest/example.c) 为接入模板。

`reward_quests()` 不是纯粹的资格查询，也不是事务：

1. 先收集任务物品：非堆叠物品被销毁，堆叠物品扣减数量，并累加已交付计数。数量不足时也可能先收下部分物品。
2. 再检查击杀数量和 `check_completion_conditions()`；未满足时，已收物品及计数不会回滚。
3. 条件满足后移除待办、记录已完成，并调用玩家 `save()`，随后显示完成消息。
4. 最后调用任务的 `reward(player, npc)`。框架不会在奖励之后再次自动保存玩家。

因此不要用交付接口做菜单预览或无副作用探测。奖励方法需安排奖励数据的保存；可能失败的奖励应由宿主保存领取状态、保证重复调用不重复发奖，并提供失败补发策略。抛错不能自动恢复已收物品或已完成记录；涉及贵重道具时，宿主应按自己的存档机制设计完整交付流程。

### 与自由任务的边界

普通任务的 `is_quest()`（旧名 `isQuest()`）只表示任务身份，不表示接入自由任务消息服务。`EVER_QUEST_D` 自动收集信息时要求对象的 `is_quest()` 为真，且公开提供 `register_information()`；宿主自由任务仍需实现该服务要求的消息与生命周期接口。普通领取型任务不要仅为通过扫描而添加空注册方法，两套服务可以按需分别接入。

自由任务服务的任务配置为 `EVER_QUEST` / `EVER_QUEST_DIR`；宿主负责初始化及心跳调度。它调用任务的 `startup()`，根据 `query_status()` 和 `start_time`、`finish_time`、`live_time` 推进生命周期，超期完成态会转为错误态。状态、超时常量和具体事件以 [服务源码](../system/daemons/ever_quest_d.c) 为准；仅设置 `is_quest()` 不会自动获得完整任务行为。
