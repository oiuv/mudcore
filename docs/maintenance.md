# 版本管理与升级验证

## 版本来源

框架版本定义在 [include/mudcore.h](../include/mudcore.h)：

| 宏 | 当前值 | 用途 |
| --- | --- | --- |
| `MUDCORE_VERSION` | `"2.0.0-dev"` | 日志、诊断、展示完整版本号 |
| `MUDCORE_VERSION_MAJOR` | `2` | 判断主版本兼容范围 |
| `MUDCORE_VERSION_MINOR` | `0` | 判断兼容功能版本 |
| `MUDCORE_VERSION_PATCH` | `0` | 判断兼容修复版本 |

这些宏描述框架自身，宿主不应覆盖。FluffOS 版本与游戏版本单独管理，不能由框架版本推断驱动能力。

全局头文件已包含 `<mudcore.h>` 后，LPC 中可直接使用 `MUDCORE_VERSION`。条件编译使用数字宏，不比较版本字符串；兼容更早、尚无版本宏的框架时，先用 `#ifdef MUDCORE_VERSION` 检查。

版本宏在对象编译时展开。框架升级后，仍在运行的旧对象不会自动获得新的宏值；按宿主流程重编译受影响对象或重启，并记录实际框架提交。

## 驱动支持范围

Git 提交（commit）`fb1549ba83ac3219e91efdbf662dc4c9c2bf78ae` 之后的 mudcore 版本最低要求 UTF-8 FluffOS `v2026.0712.3`，不再支持更早的驱动。该提交及之前的框架版本仍保留原有的旧驱动兼容策略。后续开发不为旧驱动维护兼容分支，源码采用 `.lpc` 优先规范，现有 `.c` 不批量改名；依据及模块能力要求见 [接入指南](integration.md#源文件与驱动能力)。

老 MUD 可升级驱动后使用后续框架版本，也可保留旧驱动并将框架固定到上述提交或更早的提交。使用 Git 子模块时，宿主应将子模块指针固定到选定的历史提交，并按该版本的文档验证实际驱动与模块能力；固定历史版本不会自动获得后续更新，也不承诺向旧版本回移修复。

后续采用更晚版本才有的核心必需特性时，须同步提高最低驱动版本并记录宿主升级要求；可选模块注明自身额外版本和包要求。发布验证记录实际驱动版本、提交号及启用的包，覆盖声明的最低版本和目标部署版本；未执行的版本验证应明确列出，不能将支持范围表述为全版本测试通过。

## 何时升级版本

采用 `主版本.次版本.修订号`，以对宿主的兼容影响决定：

| 变化 | 版本示例 | 典型情况 |
| --- | --- | --- |
| 不兼容升级 | `1.x.y` → `2.0.0` | 移除公共接口、修改调用约定、默认行为或存档格式，需要宿主迁移 |
| 兼容的新功能 | `2.0.0` → `2.1.0` | 新增可选组件或接口，现有宿主调用继续有效 |
| 兼容的问题修复 | `2.1.0` → `2.1.1` | 修复错误且不要求调整既有受支持用法 |

安全或权限修复也要评估兼容影响，不能仅因提交前缀是 `fix:` 就归入修订号。文档、排版和日常提交先归入“未发布”，不为每个提交单独递增版本。

`2.0.0-dev` 表示正在准备的开发版本，不是已经发布的 `2.0.0`。本轮包含外部服务启停方式和登录、数据库授权调整，因此按新的主版本整理迁移说明。历史 README 的 `v1.6.*` 只作为旧版本线索，不补造已发布的 `1.6.0` 标签。

正式发布时去掉 `-dev`；如需候选版本，可使用 `2.0.0-rc.1`。同一开发版本下可能有多个提交，定位具体构建还需提交号。数字宏不区分开发版、候选版和正式版，发布状态以完整版本字符串及 Git 标签为准。

## 发布时同步维护

1. 在 `include/mudcore.h` 更新版本字符串和三个数字宏。
2. 将 [CHANGELOG.md](../CHANGELOG.md) 的对应未发布内容整理为带版本和日期的条目，列出新增、修复、兼容影响及迁移链接。
3. 同步 README、AGENTS.md、接入指南和本文的框架版本及最低驱动要求；公共签名、默认值、权限或存档约定变化要更新相应接口文档。
4. 对修改的 LPC / 头文件格式化并执行检查，再运行隔离回归和受影响宿主的验证。
5. 提交框架变更，在确定发布的提交上创建对应的 Git 标签，如 `v2.0.0`；已经发布的标签不移动。
6. 宿主更新到这个框架提交，分别提交子模块指针和自己的接入变更。

开发变更可以先提交而不发布版本；创建或推送标签属于单独的发布操作。遵循 `.lpc` 优先的源码规范及格式化要求，见 [AGENTS.md](../AGENTS.md)。

## 宿主升级流程

升级框架前记录宿主、框架及驱动版本/提交号，确认驱动满足目标框架版本的最低驱动要求与所选组件的包要求，阅读更新日志及 [兼容迁移说明](dependency-boundary.md)。保留宿主自定义覆盖和配置，需要迁移存档时另外准备数据备份。

先在测试宿主验证目标框架版本。minimud 用于验证默认接入，已有 MUD 用于验证自身覆盖和实际启用的模块；一个宿主通过不能替代另一个宿主的结果。

在宿主根目录运行隔离测试，驱动路径替换为实际位置：

```sh
node mudcore/tests/run.mjs /absolute/path/to/driver
```

Windows 示例：

```powershell
node mudcore/tests/run.mjs bin/driver.exe
```

总入口依次运行 default、overrides、minimal、custom，四组均通过且运行器退出码为 `0` 才算成功；要求、产物位置和已知边界见 [测试说明](../tests/README.md)。不要把各组检查数之和当作独立业务场景数量。组合套件可用 `node mudcore/tests/contracts.mjs <driver路径>` 单独复测。

组件变更同步 [架构规范](architecture.md)、[模块契约](module-contracts.md) 及接口手册。最小组合需检查未选文件缺席、宿主覆盖、已选协作者错误、登录/保存/重连；启用 parser 的默认组合继续回归。仅关闭编译选项的测试不能宣称裁剪驱动已通过；权限来源诊断不能代替宿主授权拒绝测试。

再按实际启用能力完成宿主验证：

| 范围 | 验证内容 |
| --- | --- |
| 基础接入 | 驱动启动、入口对象及所需模块加载，检查调试和错误日志 |
| 默认登录 | 新账号创建、正确与错误密码、退出后再登录、断线重连 |
| 存取 | 玩家 UID/EUID 与存档路径正确，保存后重读，临时属性不写入存档 |
| 命令与内容 | 基础命令、管理员权限、房间移动、命令/谓词重载及使用到的源码扩展名 |
| 宿主覆盖 | 实际使用的组件和 daemon 别名、master 权限策略继续生效 |
| 可选能力 | 已启用的网络、数据库、Intermud 或外部命令按各自接口验证 |

网络回归可优先使用本机替身，避免测试依赖真实运营服务。全量编译只能说明对象能够编译，不能代替登录、持久化或协议行为验证。

## 同步多个宿主

子模块 gitlink 只记录提交号，不包含未提交的文档或代码。可以先在当前框架工作区完成修改与测试，但正式同步时应先生成框架提交，再让当前 MUD、minimud 等宿主检出并验证该提交，最后提交各自的 gitlink。无需在多个框架检出中分别复制和提交同一批修复。

不要为了更新 mudcore 顺带升级无关子模块。更新过程中保留各宿主自己的脚本、配置与未提交修改；发布记录至少包含框架版本、提交号、驱动信息、测试命令和未验证范围。具体历史问题可从 Git 与更新日志追溯，临时审查报告不作为长期使用手册。
